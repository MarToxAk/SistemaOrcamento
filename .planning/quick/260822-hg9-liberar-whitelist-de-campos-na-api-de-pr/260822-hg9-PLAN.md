# Quick Task 260822-hg9 — Liberar whitelist de campos na API de produtos do Athos

## Objetivo

Permitir que produtos criados/editados via API nasçam com depósito vinculado e com os campos fiscais/estoque que hoje exigem correção manual no Athos.

Campos a liberar: `iddeposito`, `estoquedeposito`, `cfopsat`, `idunidadetrib`, `margemvenda1`, `estoqueminimo`.

## Descoberta crítica — são TRÊS allowlists, não uma

O enunciado do bug fala apenas dos DTOs, mas a investigação mostrou que a superfície de escrita tem três camadas independentes. Corrigir só o DTO troca um bug visível (400) por um bug **silencioso** (200 sem persistência):

| # | Camada | Arquivo / símbolo | Efeito se não for alterada |
|---|--------|-------------------|----------------------------|
| 1 | Validação HTTP | `CreateProdutoDto` (`create-produto.dto.ts`) | 400 `property X should not exist` |
| 2 | Colunas do INSERT | `optionalFields` em `criarProduto` (`athos-produto.service.ts`, ~linha 138) | POST retorna 201 e **descarta** o campo |
| 3 | Colunas do UPDATE | `ALLOWED_UPDATE_FIELDS` em `editarProduto` (`athos-produto.service.ts`, ~linha 282) | PATCH retorna 200 e **descarta** o campo |

`UpdateProdutoDto` é `PartialType(CreateProdutoDto)` — não precisa ser editado. Adicionar o campo em `CreateProdutoDto` já o disponibiliza no PATCH.

## Decisões de tipagem (seguir os campos irmãos já existentes no DTO)

`produto.types.ts` declara várias colunas numéricas como `string | null` (o driver `pg` retorna `numeric` como string), então o tipo da row **não** é o guia. O guia é o campo irmão já existente no mesmo DTO:

| Campo | Decorators | Campo irmão que define o padrão |
|-------|-----------|--------------------------------|
| `iddeposito` | `@IsOptional() @Type(() => Number) @IsInt()` | `idunidade` |
| `idunidadetrib` | `@IsOptional() @Type(() => Number) @IsInt()` | `idunidade` |
| `estoquedeposito` | `@IsOptional() @IsString()` | `estoqueloja` |
| `estoqueminimo` | `@IsOptional() @IsString()` | `estoqueloja` |
| `margemvenda1` | `@IsOptional() @Type(() => Number) @IsNumber() @Min(0)` | `valorvenda1` + `descontomaximo` |
| `cfopsat` | `@IsOptional() @IsString()` | `idcfopsaida` |

## Restrições (não violar)

- **Não pré-validar FK de `iddeposito`.** O padrão existente só chama `validarFkExiste` para `iddepartamento`, `idgrupo` e `idmarca`. `idunidade` e `idfornecedor` não são pré-validados — caem no catch de `23503` que já converte em 422. `iddeposito` segue esse mesmo caminho. O nome da tabela de depósito não foi verificado no banco; não inventar um.
- **Não adicionar `statusproduto`/`vendeproduto` ao `ALLOWED_UPDATE_FIELDS`.** Ficam de fora de propósito — o endpoint `alterarStatusProduto` os gerencia.
- **Não incluir os novos campos em `OPERATIONAL_DEFAULTS`, `COST_DEFAULTS` nem `FISCAL_FIELDS`.** Esta tarefa apenas libera os campos; não define defaults automáticos para eles.
- Manter a ordem/estilo dos campos existentes (`@ApiPropertyOptional` com `example` e `description` em cada um).

### T3. CHECKPOINT — verificação manual contra o Athos real

**Tipo**: `checkpoint:human-verify` (bloqueante)

**Por que é manual**: os testes desta tarefa são unitários com `pg` mockado. A persistência real depende de conexão viva com o banco Athos (`ATHOS_PG_*`), indisponível neste ambiente de execução. Só o operador pode confirmar a gravação.

**O que foi construído**: os seis campos foram liberados nas três allowlists (DTO, INSERT e UPDATE) da API de produtos.

**Como verificar** (escolher um produto de teste, não um produto de venda real):

1. **PATCH** — enviar contra o backend, substituindo `{ID}` por um produto de teste e `{TOKEN}` pelo `ATHOS_API_TOKEN`:
   ```
   curl -i -X PATCH "http://localhost:3001/api/athos/produtos/{ID}" \
     -H "Content-Type: application/json" \
     -H "x-api-token: {TOKEN}" \
     -d '{"iddeposito":1,"estoquedeposito":"5","cfopsat":"5102","idunidadetrib":2,"margemvenda1":30,"estoqueminimo":"2"}'
   ```
   Esperado: **200** (antes do fix: 400 `property iddeposito should not exist`).

2. **Persistência** — confirmar no Athos (tela do produto ou `SELECT iddeposito, estoquedeposito, cfopsat, idunidadetrib, margemvenda1, estoqueminimo FROM produto WHERE idproduto = {ID}`) que os seis valores foram realmente gravados. Este passo é o que distingue o fix real do falso-positivo: 200 sem gravação significa que alguma das três camadas ficou para trás.

3. **POST** — criar um produto de teste enviando `descricaoproduto` + `iddeposito` e confirmar que ele nasce com depósito vinculado, sem correção manual no Athos.

4. **FK inválida** — enviar `iddeposito` inexistente (ex.: `999999`) e confirmar que a resposta é **422** (não 500).

**Resume signal**: responder "aprovado" ou descrever o que falhou (incluindo o código HTTP e o resultado do SELECT).
