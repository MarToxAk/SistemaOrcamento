# Phase 260723-h65: Auto-configuracao dos webhooks de confirmacao de pagamento EFI Summary

**Auto-registro do webhook PIX no boot da EFI (OnModuleInit, nao-bloqueante) + correcao de bug real: pagamentos por cartao de credito de orcamentos agora sao confirmados via rota/payload dedicados em vez de caírem silenciosamente na rota do PIX**

## Performance

- **Duration:** ~35 min
- **Tasks:** 3 de 4 concluidas (Task 4 e checkpoint humano pos-deploy, pendente)
- **Files modified:** 8 (2 criados: migration.sql + efi.card-webhook.test.ts; 6 modificados)

## Accomplishments
- `EfiService` implementa `OnModuleInit` e chama `registerPixWebhook()` no boot, registrando automaticamente a URL do webhook PIX na EFI (`PUT /v2/webhook/{chave}`) — nunca derruba o boot mesmo sem credenciais, com URL local, ou se a EFI responder erro
- Corrigido bug real de producao: `createCardPaymentLink()` apontava `notification_url` para a rota do PIX (payload `{pix: [...]}`), que nunca reconhecia o payload de cartao (`{notification: token}`) da API Cobrancas — pagamentos por cartao de orcamentos (CARTAO_2X) nunca eram confirmados automaticamente
- Nova rota `POST /integrations/efi/webhook/payment/card` + `EfiService.processCardWebhook()`, seguindo o mesmo padrao de troca de token (`GET /v1/notification/:token`) ja usado e validado pelo fluxo de boleto
- Novo campo `Quote.cardChargeId` (com migration idempotente) permite localizar o orcamento a partir do `charge_id` retornado pela EFI
- Idempotencia dupla contra reenvios da EFI: checagem de `paymentConfirmedAt` e de `PaymentTransaction.externalId` existente, ambas retornando cedo sem reprocessar
- Fluxo de boleto (`cobranca.service.ts`/`cobranca.controller.ts`) nao foi tocado — validado sem regressao

## Decisions Made
- `registerPixWebhook()` le as variaveis de ambiente diretamente via `config.get()` (nunca `getRequiredConfig`), pois este metodo tem o requisito explicito de nunca lancar excecao
- Pagamento de cartao tratado como quitacao integral do saldo restante (`paymentAmount = max(total - paidTotal, 0)`), pois o link de cartao sempre e gerado pelo valor total do orcamento
- Idempotencia implementada com dupla checagem (Quote.paymentConfirmedAt + PaymentTransaction.externalId) antes de qualquer escrita, prevenindo tanto reprocessamento logico quanto violacao do unique constraint

## Deviations from Plan

### Auto-fixed Issues

Nenhum desvio das regras 1-3 (bug/funcionalidade critica ausente/bloqueio) foi necessario — o plano foi extremamente detalhado e a implementacao seguiu literalmente file-by-file, linha-por-linha como especificado.

**1. [Ambiente - nao e desvio de codigo] `npx prisma generate` reporta EPERM ao renomear o binario do query engine no Windows**
- **Encontrado durante:** Task 2 (verificacao `prisma generate`)
- **Causa:** Um servidor de desenvolvimento (`ts-node-dev`, processo ja em execucao antes desta sessao, iniciado externamente via `npm run dev`) mantem o arquivo `node_modules/.prisma/client/query_engine-windows.dll.node` mapeado em memoria, impedindo o rename atomico que o Prisma CLI faz ao copiar o novo binario
- **Impacto real:** Nenhum — a geracao dos tipos TypeScript do Prisma Client (`index.d.ts`) e feita via parser separado (wasm) e NAO depende do binario do query engine; confirmado via `grep -n "cardChargeId" node_modules/.prisma/client/index.d.ts`, que retornou multiplas ocorrencias do campo corretamente tipado antes e depois da tentativa de generate
- **Acao tomada:** Nao matei o processo do servidor de desenvolvimento do usuario (fora de escopo e potencialmente destrutivo para uma sessao de trabalho paralela do usuario); prossegui com `tsc --noEmit`, que passou sem nenhum erro, confirmando que os tipos estavam corretos
- **Recomendacao:** Ao rodar `prisma generate` de verdade antes do proximo deploy (ou parar o `npm run dev` local), o binario do engine sera sincronizado normalmente; isso nao bloqueia o deploy real, que roda `prisma migrate deploy` + `prisma generate` em um container limpo via `bootstrap-runtime.sh`
