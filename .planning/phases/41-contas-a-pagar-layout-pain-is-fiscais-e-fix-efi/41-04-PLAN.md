### Estado e derivacao da ordenacao (dentro de `ContasReceberDashboard`)

```typescript
type SortKey = "nome" | "total_devido" | "total_atrasado";
type SortDir = "asc" | "desc";

const SORT_OPTIONS: { value: SortKey; label: string }[] = [
  { value: "total_atrasado", label: "Valor Vencido" },
  { value: "total_devido",   label: "Valor em Aberto" },
  { value: "nome",           label: "Nome" },
];

const [sortBy, setSortBy] = useState<SortKey>("total_atrasado");
const [sortDir, setSortDir] = useState<SortDir>("desc");
```

Defaults escolhidos para reproduzir exatamente a ordem que o backend ja entrega hoje (`ORDER BY total_atrasado DESC NULLS LAST, total_devido DESC`, athos.service.ts:1869): antes de qualquer clique, a tela nao muda de aparencia.

Derivacao aplicada **depois** do filtro de busca existente (page.tsx:96-103) e sobre uma copia do array, nunca mutando `clientes`:

```typescript
const clientesOrdenados = [...clientesFiltrados].sort((a, b) => {
  const mult = sortDir === "asc" ? 1 : -1;
  if (sortBy === "nome") {
    return a.nome_cliente.localeCompare(b.nome_cliente, "pt-BR") * mult;
  }
  return (a[sortBy] - b[sortBy]) * mult;
});
```

O grid de cards passa a mapear `clientesOrdenados`. As condicoes de estado vazio continuam avaliando `clientes.length` e `clientesFiltrados.length` (mesmas copys de hoje, page.tsx:227-234).

### Controle visual

`form-select form-select-sm` com as tres opcoes de `SORT_OPTIONS`, precedido do rotulo "Ordenar por" em `small text-muted`, seguido de um `button` icone `btn btn-sm btn-light border` com `title="Alternar direção da ordenação"` exibindo `bi bi-sort-down` quando `sortDir` e `desc` e `bi bi-sort-up` quando e `asc`. Posicionar na linha de acoes do cabecalho (page.tsx:141-175), entre o `input-group` de busca e os botoes de `STATUS_OPTIONS`. Nenhuma requisicao de rede e disparada por esses controles — a ordenacao e instantanea sobre os dados ja carregados.

### Destaque de inadimplencia antiga (D-10)

Classe adicionada ao bloco `<style>` da pagina, junto de `.bg-orange` e `.bg-danger-soft`:

```css
.status-border-critico { border-left: 4px solid #ee3637; }
```

Aplicada ao `div.card` de cada cliente quando `cliente.maior_atraso_dias !== null && cliente.maior_atraso_dias > 90`. O nome segue o padrao `.status-border-{chave}` ja estabelecido no Kanban (decisao de 2026-05-15 registrada em STATE.md).

### Fora de escopo, explicitamente

- Nao adicionar uma opcao de ordenacao por "pago". O eixo de status ja e coberto pelos botoes `STATUS_OPTIONS` (AVC/VEN/REC/CAN), que continuam intactos; a ordenacao opera dentro do recorte que o filtro ativo produziu.
- Nao forcar clientes criticos para o topo da lista: isso brigaria com o criterio de ordenacao que o operador acabou de escolher. O destaque e cromatico, coexiste com qualquer ordem (resolucao de D-10 registrada no 41-UI-SPEC.md).
- Nao alterar `getBadgeClass`/`getBadgeLabel`, `PasswordGate`, `STATUS_OPTIONS`, nem `contas-receber/[idcliente]/page.tsx`.
