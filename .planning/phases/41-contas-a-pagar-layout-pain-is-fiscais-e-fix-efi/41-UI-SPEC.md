## Design System

| Property | Value |
|----------|-------|
| Tool | none — no shadcn/Tailwind in this project. Component library is **Bootstrap 5.3.2 + Bootstrap Icons 1.11.1, loaded via CDN** (`<link>`/`<Script>` tags inside `page.tsx` itself), consistent across the whole app. Registry safety gate: not applicable. |
| Preset | not applicable |
| Component library | Bootstrap 5 (CDN) — cards, badges, alerts, buttons, input-group, progress, spinner-border, dropdown/select |
| Icon library | Bootstrap Icons 1.11.1 (`bi bi-*` classes, CDN) — no emoji per brand skill, except the standing exception (`✅` on realtime payment toasts elsewhere in the app, not used on this dashboard) |
| Font | System UI stack (`--font-ui` from brand skill: `"Inter", "Segoe UI", system-ui, ...`) — no webfont is loaded for this page; resolves through OS fonts, matches existing `page.tsx` |

**Why not shadcn:** this phase redesigns one page inside an otherwise 100%-Bootstrap-CDN app (`grep` for `btn btn-`/`badge bg-`/`alert alert-` across `contas-receber/` returns 70 matches across the 2 existing files, zero Tailwind/shadcn footprint anywhere in `apps/frontend`). Introducing a second component system for a single dashboard would fragment the app's visual language and is out of this phase's boundary (41-CONTEXT.md scopes this strictly to the existing dashboard). Executor must continue in Bootstrap 5.3.2.

**Primary visual anchor:** the **Painel de boletos consolidados** (D-06) is the focal point of the redesigned page — placed at the top, above the summary cards, with a larger/more prominent card treatment (full-width, taller row density) than the 4 summary cards below it. The summary cards are the secondary anchor (glanceable KPIs), and the sortable client list remains the tertiary, scrollable body of the page. This ordering resolves the competition between the three new/changed sections: boletos panel (top, largest) → summary cards (below, compact grid) → client list (below that, unchanged position).

## Spacing Scale

Declared values (must be multiples of 4) — mapped onto Bootstrap's native spacer utilities so the
executor never hand-writes inline `style={{ margin/padding }}`:

| Token | Value | Bootstrap utility | Usage |
|-------|-------|--------------------|-------|
| xs | 4px | `p-1` / `gap-1` | Icon-to-label gaps (e.g. `bi bi-cash-stack me-1`) |
| sm | 8px | `p-2` / `gap-2` / `g-2` | Compact inline spacing (badge groups, filter button row) |
| md | 16px | `p-3` / `gap-3` / `g-3` | Default card padding, grid gutters (matches existing `row g-3`) |
| lg | 24px | `p-4` / `mb-4` | Section padding (matches existing `.orcamento-section p-4`, `mb-4` between sections) |
| 2xl | 48px | `p-5` | Major break — reserved for empty-state vertical padding (matches existing `py-5` loading spinner block) |

Exceptions:
- **32px (xl) and 64px (3xl) have no native Bootstrap 5 utility** (Bootstrap jumps `p-4`=24px → `p-5`=48px). If a 32px gap is genuinely needed (e.g. spacing the new boletos panel from the summary cards above it), use `mb-4` (24px, matches existing card-to-card rhythm) rather than introducing a one-off custom class — do not add a `.gap-8`/`.p-8` utility for this phase; 24px is close enough and keeps the page visually consistent with itself.
- 44px icon-only touch targets: not applicable — this is a desktop-first internal financial tool (password-gated, no mobile-specific interaction pattern established for this page), existing buttons are `btn-sm` sized for mouse use.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 13px | 700 (bold) | 1.3 |
| Body | 16px | 400 (regular) | 1.5 |
| Metric / card value | 22px | 700 (bold) | 1.2 |
| Page title | 28px | 700 (bold) | 1.15 |

Only **two weights** are declared for this phase: **400 (regular)** for body/paragraph/muted text,
**700 (bold)** for everything currently rendered as `fw-bold` or `fw-semibold` in the existing
page (e.g. `<h4 className="fw-bold text-primary">`, `<strong>{cliente.nome_cliente}</strong>`).
**Do not introduce a distinct 600 (semibold) instance in new code** — the existing `fw-semibold`
className on inline value pairs (page.tsx:262 `<span className="fw-semibold">`) is grandfathered
visual debt, not a pattern to extend; new elements added by this phase (sort control label, aging
bucket cards, boletos-panel row values, NFS-e badges) use `fw-bold` (700) for emphasis, matching
the card-value precedent, to keep the two-weight contract clean going forward.

Sizes map to the existing Bootstrap/brand-skill scale: Label ≈ `--fs-xs` (0.78rem), Body ≈ current
page-level `font-size: 1.02rem` (page.tsx:312, kept as-is), Metric ≈ `--fs-lg`/h4 (`fw-bold`
summary-card numbers already at this size), Page title ≈ current `<h3>` "Contas a Receber" header.

### Aging / status semantic palette (extends the base 60/30/10 — required by D-07/D-10)

This dashboard is a status-dense monitoring surface with more than one semantic axis (payment
status, aging severity, NFS-e state) — the base 4-role table above covers surface color; the
table below is the closed, prescriptive palette for every status pill so the executor never
picks an ad-hoc color:

| Status pill | Color | Class |
|-------------|-------|-------|
| Em dia (0 dias atraso) | green | `badge bg-success` |
| 1-30 dias atraso | amber | `badge bg-warning text-dark` |
| 31-60 dias atraso | orange | `badge bg-orange text-white` (existing custom `.bg-orange { background-color: #fd7e14 }`, page.tsx:320) |
| 61-90 dias atraso | red (soft) | `badge` with `background-color: var(--danger-soft, #ff6b6b)` — new, add as a scoped inline style or one new utility class `.bg-danger-soft` |
| 90+ dias atraso (D-10 emphasis tier) | red (brand) + left-border accent | `badge bg-danger` **plus** a `4px` left-border card accent stripe (reuse the exact `.status-border-{statusKey}` pattern already established on the Kanban board, per `STATE.md` decision "borda superior do card via .status-border-{statusKey}") — here as `.status-border-critico { border-left: 4px solid var(--danger, #ee3637); }` on the client card, not the badge |
| Boleto pendente | amber | `badge bg-warning text-dark` |
| Boleto pago | green | `badge bg-success` |
| Boleto cancelado | gray | `badge bg-secondary` |
| NFS-e completa (todos os títulos do boleto emitidos) | green | `badge bg-success` |
| NFS-e parcial (alguns títulos emitidos, outros não) | amber | `badge bg-warning text-dark` |
| NFS-e pendente (nenhum título emitido) | gray | `badge bg-secondary` |

**D-10 resolution (Claude's Discretion, decided):** visual emphasis for long-overdue clients uses
**two combined, non-conflicting mechanisms** — (1) the aging badge color scales through 5 tiers as
above (this alone gives immediate scannability), and (2) only the most severe tier (90+ dias)
additionally gets a `4px` left-border accent stripe on its client card. A forced re-sort to the
top was explicitly rejected: D-01 already gives the user an explicit multi-criteria sort control,
and forcing a position override would silently fight whatever sort key the user just chose — a
color/border cue coexists with any sort order without contradicting it.
