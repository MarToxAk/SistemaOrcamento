### Consulta 2 — agregados fiscais (NOVA, sem `LIMIT`, sem parametros)

```sql
SELECT
  SUM(CASE WHEN TRIM(cr.statusconta) = 'VEN' AND (CURRENT_DATE - cr.datavencimento::date) BETWEEN 1 AND 30 THEN cr.valor ELSE 0 END) AS aging_1_30,
  SUM(CASE WHEN TRIM(cr.statusconta) = 'VEN' AND (CURRENT_DATE - cr.datavencimento::date) BETWEEN 31 AND 60 THEN cr.valor ELSE 0 END) AS aging_31_60,
  SUM(CASE WHEN TRIM(cr.statusconta) = 'VEN' AND (CURRENT_DATE - cr.datavencimento::date) BETWEEN 61 AND 90 THEN cr.valor ELSE 0 END) AS aging_61_90,
  SUM(CASE WHEN TRIM(cr.statusconta) = 'VEN' AND (CURRENT_DATE - cr.datavencimento::date) > 90 THEN cr.valor ELSE 0 END) AS aging_90_mais,
  SUM(CASE WHEN TRIM(cr.statusconta) = 'AVC' AND (cr.datavencimento::date - CURRENT_DATE) BETWEEN 0 AND 7 THEN cr.valor ELSE 0 END) AS a_vencer_7d,
  SUM(CASE WHEN TRIM(cr.statusconta) = 'AVC' AND (cr.datavencimento::date - CURRENT_DATE) BETWEEN 0 AND 15 THEN cr.valor ELSE 0 END) AS a_vencer_15d,
  SUM(CASE WHEN TRIM(cr.statusconta) = 'AVC' AND (cr.datavencimento::date - CURRENT_DATE) BETWEEN 0 AND 30 THEN cr.valor ELSE 0 END) AS a_vencer_30d,
  COUNT(DISTINCT CASE WHEN TRIM(cr.statusconta) = 'VEN' THEN cr.idcliente END) AS clientes_inadimplentes,
  COUNT(DISTINCT cr.idcliente) AS clientes_com_titulo_aberto
FROM conta_receber cr
WHERE TRIM(cr.statusconta) IN ('AVC', 'VEN')
```

### Consulta 3 — recebido no mes corrente (NOVA, sem parametros)

```sql
SELECT COALESCE(SUM(cre.valorpago), 0) AS total_recebido_mes
FROM conta_recebida cre
WHERE cre.datapagamento::date >= date_trunc('month', CURRENT_DATE)::date
  AND cre.datapagamento::date < (date_trunc('month', CURRENT_DATE) + INTERVAL '1 month')::date
```

Fonte da coluna: DDL de `conta_recebida` em `.planning/Discussão de Fase - Contas a Receber.md` — `idcontareceber`, `valorpago monetario`, `datapagamento dmdata`. A tabela `conta_receber` **nao** possui data de pagamento; e por isso que o recebido do mes sai de `conta_recebida`.

### Restricoes das consultas novas

- O Athos roda PostgreSQL 9.0.5: a agregacao condicional usa `CASE WHEN ... THEN ... ELSE 0 END` dentro de `SUM`/`COUNT(DISTINCT ...)`, sintaxe suportada nessa versao. Nao usar a clausula de agregado condicional introduzida no PostgreSQL 9.4.
- As duas consultas novas nao recebem nenhum valor vindo do usuario: sao SQL constante, com zero parametros. O parametro `statusFiltro` continua exclusivo da consulta principal de clientes.
- As duas consultas novas rodam **no mesmo `PoolClient`** ja aberto pela consulta principal, antes do `client.release()` no `finally`. Nao abrir uma segunda conexao.
- Os indicadores fiscais sao sempre calculados sobre `AVC` + `VEN`, independentemente de `statusFiltro` — sao a foto fiscal da carteira, nao uma visao filtrada. Documentar isso no JSDoc do metodo.

### Taxa de inadimplencia

`taxa_inadimplencia = clientes_com_titulo_aberto > 0 ? Number(((clientes_inadimplentes / clientes_com_titulo_aberto) * 100).toFixed(2)) : 0`.

Calculada a partir dos dois `COUNT(DISTINCT ...)` da consulta 2 — que nao tem `LIMIT` — e nunca a partir do array `clientes`, que e limitado a 100 linhas (`athos.service.ts:1870`, decisao D-08 de 2026-05-21 registrada em STATE.md).

### Degradacao

As consultas 2 e 3 ficam num `try/catch` proprio: em caso de erro, `this.logger.warn(...)` e os campos novos assumem zeros (`total_recebido_mes: 0`, `taxa_inadimplencia: 0`, `aging` e `a_vencer` com todos os campos em 0). A consulta principal de clientes e o `summary` legado nao sao afetados.
